# CLAUDE.md

Contexto para Claude Code sobre el proyecto **Black Iron Barbers**. Léelo antes de proponer cambios.

## Qué es este proyecto

> Proyecto de portafolio con datos ficticios.

Sitio web de una **barbería** (cortes y servicios de barbería, más asesorías de imagen: ver «Asesorías y áreas»): catálogo de servicios, reserva de citas online y dos paneles privados:

- **Barbero** (`/panel`): ve y gestiona solo sus propias citas (Resumen con agenda de hoy y citas por confirmar; completar y cancelar es exclusivo suyo).
- **Administrador** (`/admin`): ve todas las citas (pendientes y realizadas), el barbero a cargo de cada una, gestiona servicios, categorías y empleados (barberos con su usuario) y consulta el reporte diario.

El acceso a estos paneles es solo para barberos y admin, no para clientes: el login vive en `/acceso` (antes `/login-barberos`), sin ningún enlace visible en la navegación pública, con `<meta name="robots" content="noindex, nofollow">` (igual que `/panel` y `/admin`) y bloqueado en `public/robots.txt`. La ruta vieja `/login-barberos` ya no existe (muestra 404). Esto es solo para que el sitio no "invite" a clientes a buscar el login; la seguridad real sigue estando en el back-end (JWT + roles).

Ya **no** se ofrecen servicios de mujer (uñas, pedicura, cortes de dama). Si aparece código, datos o imágenes de ese tipo, se elimina.

## Stack

- **Frontend:** React 19 + Vite + Tailwind CSS 4 + React Router 7 + React Icons
- **Backend:** Node.js + Express 5 + PostgreSQL 15 (`pg`) + `bcryptjs` + `jsonwebtoken`
- **Tests:** Vitest + React Testing Library (front) · Vitest + Supertest (back, contra una base de pruebas aislada)
- **CI:** GitHub Actions (`.github/workflows/ci.yml`) — lint, build y tests en cada push/PR
- **Infra:** Docker Compose (backend + Postgres)

## Modelo de datos

- `barberos`: `id`, `nombre`, `cargo`, `especialidad`, `foto` (ruta pública bajo `public/`, p. ej. `/Barberos/boby.jpg`; nula en los creados desde el admin: la web muestra un avatar con iniciales), `activo` (el personal que se muestra en la web)
- `usuarios`: `id`, `usuario` (único), `contrasena` (hash bcrypt), `rol` (`admin` | `barbero`), `barbero_id` (nulo para el admin), `activo`, `version_token` (INTEGER NOT NULL DEFAULT 0: versión de la sesión; el JWT lleva `v` y solo vale si coincide; sube al cambiar/restablecer la contraseña y al desactivar al usuario), `contrasena_cambiada_en` (TIMESTAMPTZ NOT NULL DEFAULT now(): último momento en que se fijó la contraseña; base de la caducidad de 60 días de los barberos; se escribe siempre desde Node, nunca con `NOW()`)
  - `nombre_perfil` (VARCHAR(40), nulo) y `foto_perfil` (VARCHAR(100), nulo; solo el NOMBRE del archivo): nombre y foto que solo existen en el dashboard (ver "Perfil del dashboard"). Nulo = se usan los públicos.
- `cambios_perfil`: `id`, `usuario_id`, `barbero_id`, `campo` (`foto` | `nombre`), `valor_anterior`, `valor_nuevo` (valores EFECTIVOS), `creado_en`, `revisado_en` (nulo = pendiente), `revisado_por`; índice parcial `idx_cambios_perfil_pendientes (barbero_id) WHERE revisado_en IS NULL`. Solo registra cambios de barberos.
- `categorias`: `id`, `nombre` (único), `slug` (único; se genera del nombre al crear y no se edita), `orden` (orden de aparición), `activo` (una categoría inactiva no aparece en la web), `clave_seed` (nulo = creada por el admin)
- `servicios`: `id`, `nombre` (único; distingue mayúsculas), `descripcion`, `duracion_min` (> 0), `precio` (>= 0; 0 se muestra como "Gratis"), `tipo` (`original` | `elite` | `vip`), `categoria_id` (→ `categorias`), `activo`, `area`, `clave_seed` (catálogo del seed: barbería y asesorías)
  - Los servicios **nunca se borran**: los del catálogo anterior (ids 1–6) quedan con `activo = false` para conservar el historial de citas. La API pública y la reserva solo ven los activos.
  - `categoria_id`, `tipo` y `descripcion` admiten NULL solo por las filas anteriores a este cambio; todo servicio activo los tiene (el admin debe completarlos para reactivar uno del catálogo anterior).
  - `clave_seed` (único, nullable): identificador estable de las filas que vienen de `backend/db/data`. El seed y la migración casan por él, no por el nombre. Nulo = creado por el admin; el seed no lo toca jamás.
- `migraciones_aplicadas`: `clave` (PK), `aplicada_en`. Registro de los pasos de datos que se ejecutan una sola vez (`catalogo-claves-seed-v1`, `catalogo-legado-desactivado-v1`).
- `citas`: `id`, `cliente`, `correo`, `telefono`, `servicio_id` (servicio PRINCIPAL: el primero de la cita), `barbero_id`, `fecha` (DATE), `hora` (TIME), `duracion_min` y `precio` (snapshot: son la SUMA de los servicios de la cita; `NOT NULL`), `estado` (`pendiente` | `completada` | `cancelada`), `creada_en`, `consentimiento_en`, `rango` (`TSRANGE` generada: `fecha+hora` hasta `fecha+hora+duracion_min`). **No hay `UNIQUE (barbero_id, fecha, hora)`** (se eliminó: no ignoraba las canceladas y no detectaba solapamientos de más de 30 min): el choque lo evita `EXCLUDE USING gist (barbero_id WITH =, rango WITH &&) WHERE (estado <> 'cancelada')` (constraint `citas_sin_solapamiento`, requiere `btree_gist`). Una cita cancelada libera el hueco.
- `cita_servicios`: `id`, `cita_id` (→ `citas`, `ON DELETE CASCADE`), `servicio_id` (→ `servicios`), `orden` (1..3), `nombre`, `duracion_min`, `precio` (snapshot al reservar); `UNIQUE (cita_id, servicio_id)`, `UNIQUE (cita_id, orden)`, índice por `servicio_id`. Toda cita tiene al menos una línea (backfill idempotente en `schema.sql`). Ver "Reserva con varios servicios".
## Asesorías y áreas

El negocio tiene dos **áreas**: `barberia` (cortes, barba…, atendidos por barberos) y `asesoria` (asesorías de imagen, atendidas por asesores). Las asesorías se reservan en la web con el mismo sistema de citas (sin WhatsApp), solas o combinadas con cortes. Los valores, códigos y comprobaciones viven en `backend/utils/areas.js` y `src/utils/areas.js` (no repetir cadenas `'asesoria'`/`'barberia'` a mano en código nuevo). `area` no es `tipo`: `servicios.tipo` (original/elite/vip) es el nivel de la oferta.

### Modelo de datos

- `area` (`barberia` | `asesoria`, `NOT NULL DEFAULT 'barberia'`, CHECK `*_area_check`) en `barberos`, `servicios` y `categorias`. Un asesor es un `barberos` con `area='asesoria'` (mismo `activo`, misma tabla de usuarios: se crea como cualquier empleado).
- **Área de una cita** = el área de su servicio PRINCIPAL (`citas.servicio_id` → `servicios.area`; `areaDeCita()` en `db/citaServicios.js`, `a.area` en `db/estadisticas.js`). Coincide con la de su profesional (lo garantizan los triggers) salvo en las citas ANTERIORES a las asesorías (los cortes 449 y 450 que hizo Camila antes de pasar a `asesoria`): ahí manda el servicio, porque es lo que se cobró, y siguen contando como cortes.
- La cita de una asesoría guarda al asesor en `citas.barbero_id`. `citas.reserva_id` (UUID, nulo = cita suelta) enlaza las DOS citas de una reserva combinada; índice parcial `idx_citas_reserva` y `EXCLUDE citas_reserva_sin_autosolapamiento (reserva_id WITH =, rango WITH &&) WHERE (reserva_id IS NOT NULL AND estado <> 'cancelada')`.
- `asesoria_gratis_usos` (`cita_id` → `citas` `ON DELETE CASCADE`, `correo_norm`, `telefono_norm`, `creado_en`): una asesoría gratis por persona. Constraints con nombre (se reconocen por `err.constraint`, nunca por el texto): `asesoria_gratis_usos_cita_id_key`, `_correo_norm_key`, `_telefono_norm_key`.
- **Triggers de emparejamiento** (no FK compuesta, para no invalidar filas anteriores): `cita_servicios_area_profesional` (CONSTRAINT TRIGGER `DEFERRABLE INITIALLY DEFERRED` AFTER INSERT en `cita_servicios`: valida al COMMIT que el servicio y el profesional sean del mismo área) y `citas_area_barbero` (BEFORE UPDATE OF `barbero_id`: la reasignación del admin). Solo revisan líneas nuevas y reasignaciones. Error: SQLSTATE `BI001`, `err.constraint = 'cita_servicios_area_profesional'`, mensaje que empieza por `PROFESIONAL_INCOMPATIBLE:` (`esErrorAreaProfesional`).
- `servicios.clave_seed` (único, nulo = creado por el admin) es el identificador estable de los del catálogo del seed; `/api/servicios` lo expone como `clave` solo en esos (aditivo).
- **Seed** (solo inserta; idempotente): categoría "Asesorías" (`clave_seed='asesorias'`, `area 'asesoria'`) con `asesoria-gratis` ($0, 15 min, `original`), `asesoria-barba` ($45.000, 45 min, `elite`) y `asesoria-premium` ($60.000, 60 min, `vip`); descripciones en `db/data/descripciones.js`. Personal: `db/sembrarPersonal.js` siembra a Camila (`Asesora de Imagen`) con `area 'asesoria'` **solo al insertar** (en una base existente el seed no toca el área).
- **Migración única `personal-area-asesoria-v1`** (`migracionesCatalogo.js`, registrada en `migraciones_aplicadas`): marca `area='asesoria'` donde `nombre='Camila' AND cargo='Asesora de Imagen'`. Sin esa fila queda pendiente; si ya viene marcada solo se registra; **si Camila tiene citas abiertas (pendientes, o no canceladas de hoy en adelante) se ABORTA sin tocar nada y con un aviso en consola** (se reintenta en el próximo arranque). Las completadas pasadas no bloquean.
- Pruebas del esquema: `asesoriasEsquema.test.js`.

### Reglas de negocio

- **Quién atiende qué**: los asesores solo asesorías y los barberos solo barbería (el área de cada servicio sale de la base; el cliente no la declara). "Cualquier barbero" solo usa barberos activos de `barberia`; `barbero`/`barbero_id` de un asesor, o `asesor_id` de un barbero → 400 `PROFESIONAL_INCOMPATIBLE` (con `campo`).
- **Una asesoría por reserva** (400 `LIMITE_ASESORIAS` con `maximo`), dentro del límite de 3 servicios (1 asesoría + hasta 2 de barbería).
- **Reserva combinada** = DOS citas con el mismo `reserva_id` (uuid generado en Node), creadas en UNA transacción, la asesoría primero y el corte justo cuando termina (sin hueco ni solape). Una asesoría sola o un corte solo quedan con `reserva_id` NULL. Cada profesional completa o cancela solo su cita.
- **Tope de 240 min por cita** (por grupo de servicios del mismo profesional), no sumando asesoría + corte: protege el bloque continuo de un solo profesional. Siguen acotando la reserva el máximo de 3 servicios y el horario de atención (sobre la duración total encadenada). Vive en `cargarServicios` (`utils/serviciosCita.js`, devuelve `asesoria` y `barberia` con `lista` renumerada 1..n, `duracion` y `precio`). El front lo repite en `utils/carrito.js` (`evaluarAgregado`/`estadoDeTarjeta` reciben `cantidadBarberia`; solo la barbería suma).
- **Estados finales**: `completada` y `cancelada` no cambian de estado (409 `TRANSICION_INVALIDA` con `estado_actual`; repetir el mismo estado es inocuo); tampoco se **reasigna** una cita en estado final a otro profesional (409 `TRANSICION_INVALIDA`). Se aplica al leer y otra vez en el `WHERE` del `UPDATE` (carreras). Reabrir una cancelada está prohibido (decisión del propietario).
- **Reasignar** (admin, `PATCH /api/citas/:id`) a un profesional de otra área → 400 `PROFESIONAL_INCOMPATIBLE` (campo `barbero_id`), desde el controlador y, de respaldo, el trigger.

### Disponibilidad y creación de citas

- `GET /api/disponibilidad`: `servicios=`/`servicio=`, `barbero=` y `asesor=<id>`. Solo barbería: como siempre. Solo asesoría: pool = asesores activos (o `asesor=`), duración = la de la asesoría. Asesoría + barbería: una hora `t` se ofrece si hay un asesor libre en `[t, t+A)` Y un barbero libre en `[t+A, t+A+C)` y `t+A+C` cabe en el horario; las horas devueltas son las de inicio de la asesoría. Respuesta: `{ barbero_id, fecha, horas }` más `asesor_id` solo si la reserva incluye una asesoría (`null` = cualquiera). `barbero=` sin servicios de barbería, o `asesor=` sin asesoría → 400 `PROFESIONAL_INCOMPATIBLE`; profesional inexistente o inactivo → 404. 3 consultas en total.
- `POST /api/citas`: acepta `asesor_id` además de `barbero_id`; sin profesional elegido se asigna por pool del área (menos citas ese día, desempate por id; el del corte se busca desde que termina la asesoría). Una cita → respuesta plana de siempre; combinada → `{ reserva_id, citas: [asesoría, corte] }`. Transacción: `BEGIN`, `FOR SHARE` de los servicios por id, `INSERT` asesoría + líneas, `INSERT` corte + líneas, `COMMIT`. Los reintentos ante 23P01/40P01 hacen ROLLBACK completo y avanzan solo el candidato del profesional que falló (`etapa`: `asesoria`, `barberia` o `commit`). El error del trigger al COMMIT → 400 `PROFESIONAL_INCOMPATIBLE` (`campo: 'profesional'` en una combinada). Un conflicto de horario es `esConflictoDeHorario` (23P01, o 23505 salvo `asesoria_gratis_usos_*`).
- Pruebas: `reservasAsesoria.test.js` (ids 92xx), `asesoriasArea.test.js` (ids 91xx).

### Asesoría gratis: una por persona

- La gratis (`clave_seed='asesoria-gratis'`, `esAsesoriaGratis(servicio)`) es de UNA por persona, por correo **Y** teléfono: si cualquiera ya la usó, 409 `ASESORIA_GRATIS_YA_USADA`. "Usada" = toda gratis NO cancelada (pendiente, completada o pendiente vencida sin confirmar).
- **Normalización** (`utils/identidadAsesoria.js`, un solo módulo): correo = recorte + minúsculas + sin sufijo `+etiqueta` (todos los dominios) + sin puntos de la parte local solo en `gmail.com`/`googlemail.com` (este se trata como gmail.com; si quitar `+etiqueta`/puntos dejara la parte local vacía se conserva la original). Teléfono = `normalizarTelefono` (10 dígitos). `asesoria_gratis_usos` guarda esa forma; `citas.correo` conserva lo que escribió el cliente.
- **POST /api/citas** (en la transacción): tras insertar la cita de la gratis se inserta su fila de uso (la UNIQUE decide también entre dos reservas simultáneas). Un 23505 sobre las UNIQUE de correo/teléfono → ROLLBACK completo y 409 `{ error, codigo: 'ASESORIA_GRATIS_YA_USADA', servicio_id }` (el proyecto usa `codigo`, no `code`); no reintenta con otro candidato; no dice qué dato coincidió. En una combinada se revierte todo: el front puede reservar de nuevo solo el corte.
- **Cancelar libera**: `PATCH` con `estado: 'cancelada'` borra la fila de uso de ESA cita en la misma sentencia (CTE); cancelar el corte hermano no la toca; completar no libera. Ningún endpoint edita correo ni teléfono de una cita creada.
- **Comprobación temprana** `POST /api/asesorias/gratis/comprobar` `{ correo, telefono }` → 200 `{ disponible }` (400 `DATOS_INVALIDOS` genérico). Solo comodidad de UX: la verdad es el POST. Limitador por IP: 10 intentos / 15 min (`LIMITE_COMPROBAR_GRATIS_RATE`; omitido bajo `NODE_ENV=test` salvo `FORZAR_RATE_LIMIT_PRUEBA=true`); 429 `DEMASIADOS_INTENTOS` con `reintentar_en_seg`. Riesgo residual (oráculo): quien pruebe correos/teléfonos puede saber si alguno ya usó la gratis; lo acotan el formato y el límite por IP.
- **El precio de la gratis es fijo**: `PATCH /api/admin/servicios/:id` con otro precio → 409 `PRECIO_FIJO` (mandar 0 es inocuo; desactivarla sí se puede).
- Pruebas: `identidadAsesoria.test.js`, `asesoriaGratis.test.js` (ids 93xx), `rateLimitAsesoriaGratis.test.js`.

### Listados de citas, estadísticas y reportes

- **Listados** (`GET /api/citas`, `/api/admin/citas`, `/api/barbero/citas`, `agenda-hoy`, `citas-por-confirmar`; `COLUMNAS_RESERVA` en `db/citaServicios.js`): añaden `area`, `reserva_id` y `hermana` (la OTRA cita de una reserva combinada con SOLO `{ id, area, profesional (nombre público), hora_inicio, hora_fin, estado }`; `null` si no es combinada). Sin contacto, precios ni servicios de la hermana. Cada profesional sigue viendo solo sus citas.
- **`GET /api/admin/citas?area=barberia|asesoria`** filtra lista y total (inválido, vacío o repetido → 400).
- **Estadísticas** (`db/estadisticas.js`): `resumenPeriodo` devuelve `cortes` (completadas de barbería), `asesorias`, `ingresos_barberia` e `ingresos_asesoria`; `completadas` e `ingresos` son el TOTAL. `ticket_promedio`: en las cifras globales (admin) es SOLO de barbería; con un profesional es el de sus propias citas; siempre excluye precio 0. Las series por día/mes traen `ingresos`, `ingresos_barberia`, `ingresos_asesoria`, `cortes`, `asesorias` y `completadas`. En el panel de un profesional, `cortes_mes` y la tarjeta Cortes/Asesorías cuentan SU área; su dinero es el total de lo que cobró.
- **`serviciosTop`** (por línea de `cita_servicios`): `GET /api/admin/estadisticas/servicios-top?area=`; por defecto barbería; inválido/repetido → 400; la respuesta lleva `area`. El endpoint del barbero NO admite `area` (400).
- **Reporte diario**: `total_cortes` = completadas de barbería; añade `total_asesorias`, `ingresos_barberia`, `ingresos_asesoria` y `asesorias_mas_pedidas`. `ingresos` es el total, `ticket_promedio` solo de barbería, `servicios_mas_pedidos` solo de barbería. **CSV**: las filas y columnas de siempre no cambian de lugar; al final se añaden `Total de asesorías`, `Ingresos de barbería`, `Ingresos de asesorías` y la tabla `Asesoría;Cantidad;Ingresos` (mismas 3 columnas; no hay columnas nuevas).
- No hay ranking ni comparativa entre profesionales. `/api/admin/empleados` → `cortes_mes` cuenta las completadas del mes que sean del área del empleado.
- Pruebas: `panelesAsesoria.test.js`.

### Admin: empleados y servicios

- **Empleados** (`adminEmpleadosController.js`): `POST`/`PATCH` aceptan `area` (por defecto `barberia`; inválida → 400 `DATOS_INVALIDOS` con `campo`); `GET` la devuelve. Cambiar el área con citas abiertas → 409 `AREA_CON_CITAS_PENDIENTES` (con `campo: 'area'` y `citas_pendientes`; no se guarda nada). Front: selector "Área" con frase de ayuda al crear y editar, etiqueta de área en la lista y la cifra del mes rotulada "Cortes"/"Asesorías" según el área; el 409 se muestra en el campo Área (`role="alert"`, foco, enlace "Ver y reasignar sus citas") con el formulario aún usable.
- **Servicios** (`adminCatalogoController.js`): `POST`/`PATCH` aceptan `area` (por defecto `barberia`; inválida → 400). La **categoría debe ser del mismo área** (400 `CATEGORIA_AREA_INCOMPATIBLE`, `campo: 'categoria_id'`; al cambiar el área hay que mandar también una categoría del nuevo). El **área no cambia si el servicio ya tiene líneas en `cita_servicios`** (409 `SERVICIO_CON_HISTORIAL`, `campo: 'area'`); sin historial sí. La gratis sembrada: precio fijo (409 `PRECIO_FIJO`). **Los servicios con `clave_seed` (catálogo sembrado, de cualquier área) no cambian de área**: 409 `AREA_FIJA` (`campo: 'area'`; mandar el mismo valor no es un cambio); los creados por el admin siguen pudiendo mientras no tengan historial. La respuesta del admin marca `area_fija`. `GET /api/admin/servicios?area=` filtra; cada servicio y categoría del admin traen `area` y el servicio `precio_fijo`. Front: selector de área en el formulario (la lista de categorías ofrece solo las del área elegida y se limpia al cambiar de área), filtro "Área" (también limita los chips de categoría), etiqueta/columna de área y precio deshabilitado en la gratis y selector de Área deshabilitado (con su explicación) en los del catálogo base. **El admin no puede crear categorías de asesoría** (las categorías nuevas son de barbería): solo existe la sembrada "Asesorías".
- **Una asesoría creada por el admin** (sin `clave_seed`, por tanto sin `clave` pública): se puede reservar (aparece en el bloque "Añadir una asesoría" de la reserva y por la API), pero **`/asesorias` y el modal "Soy cliente nuevo" solo muestran las tres que tienen texto por `clave`**; no rompe nada (probado). Riesgos de editar las sembradas: renombrar es seguro (se une por `clave`); desactivarlas las oculta de `/asesorias` y de la reserva; cambiarles precio/duración cambia lo que se muestra y cobra (la gratis no puede cambiar de precio); su área no se puede mover (`AREA_FIJA`).

### Flujo de reserva con asesorías (`/reservar-corte`)

- **Datos**: `ReservaCorte` pide `obtenerServicios({ area: 'barberia' })`, `obtenerServiciosAsesoria()` y `obtenerBarberos()`; etiqueta las asesorías con `area: 'asesoria'`. `utils/reservaAsesoria.js`: `esAsesoria`, `esAsesoriaGratis` (por `clave`), `separarPorArea`, `estadoDeAsesoria`, `planCitas(servicios, hora)` y `normalizarReserva(resp)` (cita plana o `{ reserva_id, citas }`).
- **Paso Servicio**: `BloqueAsesoria` ("Añadir una asesoría (opcional)"): una sola y dentro del tope de 3; lo bloqueado queda con `aria-disabled` y el motivo en texto (`aria-describedby`). **Llegada por URL**: `?servicio=<id>` o `?servicios=1,2,3` aceptan ids de ambas áreas validados contra las dos listas (los que no existen se descartan con aviso; dos asesorías o un combo de barbería de más de 240 min avisan). El carrito solo se vacía si la reserva llegó por `?servicios=`.
- **Profesionales** (el paso conserva la clave `barbero`; etiqueta Barbero / Asesor/a / Profesionales): solo barbería, solo asesoría ("Cualquier asesor" + asesores) o ambos en "Tu asesor/a" y "Tu barbero". El reducer tiene `barberoId` y `asesorId` (`null` = cualquiera); solo viaja al servidor el que corresponde (`barbero_id` / `asesor_id`).
- **Fecha y hora**: `obtenerDisponibilidad(ids, fecha, barberoId, asesorId)` (el 4.º argumento solo si hay asesor). En una combinada las horas son las de inicio de la asesoría, con un texto que lo explica y `Asesoría: HH:MM – HH:MM` / `Barbería: …` (`role="status"`).
- **Resumen / ModalConfirmacion / PantallaExito**: una sección por cita y total combinado; aceptan la respuesta plana o `{ reserva_id, citas }`. El consentimiento del modal: toda la fila es la etiqueta (`min-h-11`); el checkbox sigue de 16 px.
- **Asesoría gratuita** (`hooks/useComprobarGratis.js`): con la gratis en la reserva y correo y teléfono válidos llama a `comprobar` (espera de 600 ms, cancelando la anterior). `disponible:false` (o el 409 del POST) muestra un aviso (`role="status" aria-live="polite"`, sin decir qué dato coincidió), bloquea "Confirmar reserva" y ofrece "Quitar asesoría gratuita" (vuelve a Fecha y hora con la hora por elegir, o a Servicios si era lo único) y "Elegir otra asesoría". Si `comprobar` falla o da 429, NO bloquea: decide el POST.
- **Errores**: `PROFESIONAL_INCOMPATIBLE` vuelve al paso de profesionales; `LIMITE_ASESORIAS` al paso Servicio; el 409 de horario refresca la disponibilidad.

### Notas operativas y de despliegue

- **Reinicio manual de la asesoría gratis** (no hay herramienta de admin): con `pg_dump` previo, borrar la fila de uso de esa persona: `DELETE FROM asesoria_gratis_usos WHERE correo_norm = <correo normalizado> OR telefono_norm = <10 dígitos>;` (valores siempre parametrizados; el correo normalizado se calcula con `normalizarCorreo`). No toca la cita.
- **Despliegue de esta funcionalidad**:
  1. `pg_dump` previo de la base (`docker exec … pg_dump -f /tmp/x.sql` + `docker cp`).
  2. El esquema (`schema.sql`, aditivo e idempotente) se aplica solo al arrancar el backend; aplicarlo dos veces no cambia nada (probado sobre una restauración de desarrollo).
  3. La migración `personal-area-asesoria-v1` marca a Camila por nombre y cargo; si tiene citas abiertas se aborta con un aviso y se reintenta en el siguiente arranque.
  4. `npm run seed` inserta la categoría y las 3 asesorías (y el personal en instalaciones nuevas); es idempotente.
  5. Reconstruir el contenedor: `docker compose up -d --build backend_black_iron` (**nunca `down -v`**): el front nuevo pide `?area=barberia` y un backend anterior lo rechaza con 400.
  6. `trust proxy` y limitadores en memoria (ver arriba); con varias instancias, un almacén compartido. **`trust proxy` NO está configurado hoy y es obligatorio configurarlo bien detrás del proxy real** (`app.set('trust proxy', <nº de saltos o IP del proxy>)`, nunca `true` a ciegas): sin él `req.ip` es la IP del proxy, así que TODOS los clientes comparten el cupo del límite por IP (el de login por IP + usuario se degrada a "por usuario": un atacante podría bloquear a un barbero concreto y el tope de 100 fallos por IP bloquearía a todos). Con un valor demasiado permisivo, en cambio, el cliente podría falsear `X-Forwarded-For` y esquivar los límites. En Docker en desarrollo `req.ip` es la IP de la pasarela, igual para todos.
  7. `backend/Dockerfile` usa `node:22-alpine` (v22.23.3 verificada en el contenedor; igual que el CI).
  8. `VITE_WHATSAPP_NUMERO` en el `.env` de producción (solo para el botón flotante).
- **Prueba de instalación limpia** (hecha en la fase 7): base vacía → arranque → seed → reservas reales (asesoría sola, combinada, gratis y su 409) → segundo arranque + segundo seed sin duplicar nada; y restauración de un `pg_dump` de desarrollo + `schema.sql` dos veces con los hashes de las citas intactos.

## Verificación de correo

Reservar exige **demostrar que el correo es de quien reserva**: un código de 6 dígitos que llega por correo y que se canjea por un comprobante firmado de un solo uso. Es obligatoria en TODAS las reservas (corte, asesoría, combinada y asesoría gratis). Cierra el riesgo de que alguien escriba el correo de otra persona y esta reciba la confirmación.

- **Flujo.** (1) `POST /api/verificacion-correo/solicitar { correo }` envía el código. (2) `POST /api/verificacion-correo/confirmar { correo, codigo }` devuelve `{ token, expira_en_seg }` (el comprobante, 30 min). (3) `POST /api/citas` lleva `verificacion_token`; el comprobante se **consume dentro de la misma transacción que crea la cita** (o las dos de una combinada: UN solo comprobante). Si la transacción falla (409 de horario, asesoría gratis ya usada, 400 de validación…) el ROLLBACK lo devuelve y el cliente reintenta con el mismo.
- **Validador único de correo** (`backend/utils/validarCorreo.js`; el front lo repite en `src/utils/correo.js`): recorte + minúsculas; rechaza espacios, comas, `;`, `< >`, comillas, saltos de línea, más de un `@`, > 254 caracteres, parte local > 64, dominio sin punto o con caracteres inválidos, TLD no alfabético. Lo usan solicitar, confirmar y `POST /api/citas` (**cambio de comportamiento:** antes bastaba `algo@algo.algo` y `a@b.com,c.d` o `x@y.com>` pasaban; ahora dan 400). `citas.correo` guarda ya el correo normalizado (recortado y en minúsculas).
- **Igualdad del correo** (comprobante ↔ cita): EXACTA tras recortar y pasar a minúsculas. Cambiar solo mayúsculas es el mismo correo; `+etiqueta` y puntos lo distinguen (`ana+1@x.com` ≠ `ana@x.com` → 400 `CORREO_NO_COINCIDE`). La normalización agresiva (Gmail, `+etiqueta`) es solo de `identidadAsesoria`, para la asesoría gratis.
- **Tablas** (`schema.sql`, aditivas e idempotentes): `verificaciones_correo` (`id`, `correo`, `codigo_hash` CHAR(64), `intentos`, `expira_en`, `usado_en`, `invalidado_en`, `creado_en`; índice `(correo, creado_en DESC)`) y `verificaciones_usadas` (`jti` con `CONSTRAINT verificaciones_usadas_jti_key UNIQUE`, `correo`, `usado_en`). Los instantes los escribe Node (reloj inyectable en pruebas), no `NOW()`. Borrado perezoso de lo vencido hace más de un día al solicitar.
- **Código.** `crypto.randomInt` (CSPRNG), 6 dígitos, vigencia **10 min**. En la base SOLO el HMAC-SHA256 (clave derivada de `EMAIL_VERIF_SECRET`, con el correo dentro del mensaje); nunca el código en claro. Un código nuevo **invalida** los anteriores del correo (`invalidado_en`).
- **Límites.** Por correo, EN LA BASE (no se reinician con el servidor; con `pg_advisory_xact_lock` por correo para que las peticiones paralelas no los burlen): espera mínima de **60 s** entre solicitudes (429 `ESPERA_REQUERIDA`) y máximo **5 códigos por hora** (429 `LIMITE_CODIGOS_HORA`), ambos con `reintentar_en_seg`. Por IP (`express-rate-limit`, en memoria): 20 solicitudes por hora y 30 confirmaciones cada 15 min (429 `DEMASIADOS_INTENTOS`; `LIMITE_VERIF_SOLICITAR_IP_RATE` y `LIMITE_VERIF_CONFIRMAR_IP_RATE`; omitidos bajo `NODE_ENV=test` salvo `FORZAR_RATE_LIMIT_PRUEBA=true`). **5 intentos por código**: el contador sube con un `UPDATE … RETURNING` atómico ANTES de comparar (diez intentos paralelos no pasan de 5) y agotarlos invalida el código aunque luego llegue el correcto.
- **Respuestas.** Solicitar: siempre `{ ok: true, reenviar_en_seg: 60 }` (no revela nada del correo); 503 `CORREO_NO_DISPONIBLE` si el envío falla (el código no queda vivo ni gasta cupo; se registra con el correo enmascarado). Confirmar: **un solo error** para código incorrecto, vencido, usado o inexistente, 400 `CODIGO_INVALIDO` (mismo trabajo en todos los casos: siempre se calcula el HMAC y se compara con `timingSafeEqual`); formato (`codigo` = exactamente 6 dígitos, solo texto) → 400 `CODIGO_FORMATO_INVALIDO` sin gastar intentos; correo inválido → 400 `CORREO_INVALIDO`.
- **Comprobante** (`utils/verificacionCorreo.js`): JWT **HS256 fijado** (`algorithms: ['HS256']`: sin `alg: none`), firmado con `EMAIL_VERIF_SECRET` (distinto de `JWT_SECRET`, validado), claims `typ: 'email-verify'`, `aud: 'black-iron-barbers:verificacion-correo'`, `iss`, `correo` (exacto), `jti`, `iat`, `exp` (30 min). Un token de login no sirve como comprobante (otro secreto y sin `typ`/`aud`) ni al revés (`verificarToken` usa `JWT_SECRET`). **De un solo uso**: el `jti` se inserta en `verificaciones_usadas` dentro de la transacción de la reserva; el UNIQUE decide entre dos reservas paralelas con el mismo comprobante (una gana, la otra recibe `VERIFICACION_INVALIDA`; `esConflictoDeHorario` excluye esa restricción).
- **`POST /api/citas`.** Tras validar el correo y ANTES de cualquier otra lógica: `VERIFICACION_REQUERIDA` (falta), `VERIFICACION_INVALIDA` (firma, `typ`, `aud`, ya usado, no es texto), `VERIFICACION_EXPIRADA`, `CORREO_NO_COINCIDE` (todos 400 con `codigo`). Las respuestas de éxito no cambian. `sembrarDemo.js` y `seedDemo.js` insertan directo en la base y no se ven afectados.
- **Sin bypass.** No hay NINGÚN modo de saltarse la verificación en el código de producción ni por `NODE_ENV=test`. **La variable `REQUIRE_EMAIL_VERIFICATION` se ELIMINÓ** (pentest, fase 0): la verificación es siempre obligatoria y ninguna variable de entorno la desactiva (si alguien la deja en su `.env`, se ignora). Las pruebas generan comprobantes REALES con `firmarComprobante` (`backend/tests/verificacionPrueba.js`; `tests/setup.js` los añade a `POST /api/citas` si la prueba no indica `verificacion_token`; las pruebas de la verificación pasan el suyo).
- **Configuración** (`config/verificacion.js`, se valida al arrancar desde `index.js`): `EMAIL_VERIF_SECRET` (obligatorio con la verificación activa: ≥ 32 caracteres, variedad real de caracteres, distinto de `JWT_SECRET`, ni el valor de ejemplo ni uno que estuvo publicado: ver «Seguridad (pentest)»). En **producción** (`NODE_ENV=production`) el back-end NO arranca si falta `EMAIL_ENABLED=true` con SMTP válido o si falta o es débil `EMAIL_VERIF_SECRET`; los errores nunca imprimen valores. Llegan al contenedor por `environment:` del compose (`EMAIL_VERIF_SECRET` sin valor por defecto: sin él el back-end no arranca). Generar el secreto: `node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"`.
- **Desarrollo: hace falta Mailpit.** Para reservar en local hay que tener `EMAIL_ENABLED=true` y `EMAIL_VERIF_SECRET` en el `.env` y Mailpit arriba (`docker compose --profile dev up -d mailpit`; el código se lee en http://localhost:8025). Sin correo habilitado, solicitar responde 503 y no se puede reservar. El código nunca se imprime en consola ni en logs.
- **Plantilla** (`plantillaCodigoVerificacion`, español, texto + HTML, todo escapado, estilos en línea): el código va solo en el cuerpo (no en el asunto), con vigencia de 10 minutos y «si no fuiste tú, ignora este mensaje».
- **Front** (`hooks/useVerificacionCorreo.js` + bloque «Verifica tu correo» en `ModalConfirmacion`): el correo y la verificación viven en `ReservaCorte` (no en el modal) para que el comprobante **sobreviva a un 409 de horario** (el modal se cierra, se elige otro bloque y no se verifica de nuevo). El comprobante solo está en memoria (nunca `localStorage`/`sessionStorage`) y no se muestra jamás. Editar el correo lo descarta en el acto (se compara recortado y en minúsculas); se descarta solo a los 30 min (5 s antes). «Confirmar reserva» está deshabilitado hasta verificar, con `aria-describedby` al motivo. Campo del código: `inputMode="numeric"`, `autoComplete="one-time-code"`, `maxLength=6`, solo dígitos. «Reenviar código» con cuenta regresiva de 60 s, «Cambiar correo», avisos con `role="alert"`/`aria-live`. Foco: al pedir el código → campo del código; al verificar → botón de confirmar. Si el servidor responde `VERIFICACION_*` o `CORREO_NO_COINCIDE` se descarta el comprobante y se vuelve a pedir el código con el modal abierto. `PantallaExito`: «Te enviamos la confirmación a <correo>». `ModalConfirmacion` guarda `onClose` en una ref: como el correo vive en el padre, cada tecla lo re-renderiza y, sin eso, el foco saltaba al campo Nombre.
- **Hallazgo (sin cambiar): `POST /api/asesorias/gratis/comprobar` es un oráculo.** Es público y responde `disponible: false` si ese correo **o** ese teléfono ya usó la asesoría gratis, **sin demostrar que sean de quien pregunta** (solo lo frena el límite de 10 por IP cada 15 min, en memoria). La UI lo llama en cuanto correo y teléfono son válidos, antes de verificar el correo. Propuesta: moverlo DESPUÉS de la verificación (exigir el comprobante, sin consumirlo, y comprobar solo ese correo) o dejar de usarlo y que decida el POST (409 `ASESORIA_GRATIS_YA_USADA`, que ya exige comprobante). El teléfono seguiría siendo sondeable con un correo propio verificado; si importa, quitarlo de la comprobación temprana.
- **Riesgos residuales.** Los límites por IP viven en memoria (se reinician con el servidor; un `trust proxy` mal configurado los degrada, ver «Notas operativas y de despliegue»); los límites por correo (60 s, 5 por hora, 5 intentos por código) no. La verificación prueba posesión del correo, no identidad.
- Pruebas: `validarCorreo.test.js`, `verificacionCorreo.test.js` (solicitar, confirmar, comprobante y límites por IP), `verificacionReservas.test.js` (ids 96xx), `verificacionConfig.test.js` (arranque y esquema); front: `VerificacionReserva.test.jsx`, `ModalConfirmacion.test.jsx` y los ayudantes `tests/verificacionPrueba.js` y `tests/ContenedorModalPrueba.jsx`.

## Autenticación y roles

- Un solo login (`POST /api/auth/login`). El JWT lleva `id`, `rol` y `barbero_id`.
- El **administrador crea el usuario y la contraseña de cada barbero** (`POST /api/admin/usuarios`). No existe registro público.
- El admin inicial se crea con el seed usando `ADMIN_USER` y `ADMIN_PASSWORD` del `.env`.
- Los usuarios se **desactivan** (`activo = false`), nunca se borran, para conservar el historial de citas.
- `verificarToken` no se fía solo del JWT: en cada petición consulta `usuarios` (y `barberos` si es barbero) y responde 401 `SESION_INVALIDA` si el usuario o su barbero están inactivos o ya no existen. Así, desactivar a un empleado invalida su token al instante (si no, seguiría valiendo hasta 8 h). El `rol` y el `barbero_id` de `req.usuario` salen de la base, no del token. Costo: una consulta por clave primaria por petición.
- Un empleado es un barbero más su usuario, y **siempre en el mismo estado**: crear, desactivar y reactivar tocan ambos en una transacción. Puede haber varios usuarios ligados al mismo barbero (datos de prueba antiguos); el listado muestra uno (el activo, o el más reciente) y `usuarios_total`.
- **El cierre de sesión voluntario siempre pide confirmación** (`hooks/useConfirmarCierreSesion.jsx` + `ModalConfirmar`, foco inicial en Cancelar; lo usan la barra lateral/cajón, el menú de usuario (admin y barbero; el del admin trae "Cambiar contraseña" y "Cerrar sesión"), Mi cuenta y la pantalla de contraseña caducada): ningún botón llama a `logout` directamente. El cierre automático (401, token vencido, contraseña caducada) NO pide confirmación y sigue con `expirarSesion` y el aviso "Tu sesión expiró".
- **Caducidad de contraseñas (solo barberos; el admin está exento y cambia la suya cuando quiera).** Constantes en un solo lugar: `backend/utils/contrasenas.js` (`VIGENCIA_DIAS = 60`, `AVISO_DIAS = 2`, longitud 8–72) junto con `estadoContrasena()`.
  - Estado = `{ estado, dias_restantes, vence_en }`. `vence_en` = fecha de Bogotá del último cambio + 60 días (el primer día en que la contraseña ya no sirve); `dias_restantes` = días de **calendario** entre hoy (Bogotá) y `vence_en`. Se cuenta por fecha y no por bloques de 24 h para que el número no dependa de la hora del cambio ni de la zona del servidor (a las 22:00 de Bogotá ya es "mañana" en UTC). `vigente`: ≥ 3 · `por_vencer`: 1 o 2 · `caducada`: 0 o menos (día 57 vigente, 58 por_vencer, 60 caducada, contando el día del cambio como 0). Se calcula en Node (`fechaBogota()` de `utils/fechas.js`).
  - **El barbero no puede cambiar su contraseña cuando quiera**: solo con `por_vencer` o `caducada`; si no, 403 `CAMBIO_NO_PERMITIDO` (se aplica en el back-end, no solo ocultando el botón).
  - El administrador puede restablecer la contraseña de un barbero en cualquier momento (`PATCH /api/admin/usuarios/:id`). Eso, y crear un empleado o un acceso, deja `contrasena_cambiada_en` en "ahora" (reinicia los 60 días). Cambiar solo `activo` no lo toca. El barbero no está obligado a cambiarla al entrar.
  - Con la contraseña `caducada` el barbero **puede iniciar sesión**, pero `verificarToken` responde 403 `CONTRASENA_CADUCADA` en todo lo demás. Solo `GET /api/auth/sesion` y `PATCH /api/auth/contrasena` usan `verificarTokenPermitiendoCaducada`. Un usuario desactivado sigue dando 401 `SESION_INVALIDA` antes que cualquier otro bloqueo.
  - `PATCH /api/auth/contrasena` exige `actual` y `nueva` (8–72) distinta de la actual. Errores (todos con `codigo`): 403 `CAMBIO_NO_PERMITIDO`, 403 `CONTRASENA_CADUCADA` (otros endpoints), 400 `CONTRASENA_ACTUAL_INCORRECTA` (400 y no 401: un 401 con token cierra la sesión en el front), 400 `CONTRASENA_IGUAL`, 400 `DATOS_INVALIDOS` (con `campo`), 429 `DEMASIADOS_INTENTOS`. Tiene limitador propio: 5 intentos **fallidos** por usuario cada 15 min (los cambios correctos no cuentan), porque quien robe un token podría adivinar la contraseña actual a golpe de intentos. Como el de citas, se omite bajo `NODE_ENV=test` salvo `FORZAR_RATE_LIMIT_PRUEBA=true` (el login también).
  - El login devuelve `vigencia` (estado de la contraseña del barbero, `null` para el admin). `GET /api/admin/empleados` añade `usuario.vigencia` (nunca hashes). El campo se llama `vigencia` (y no "contraseña") para que ninguna respuesta lleve la palabra `contrasena`.
  - Front: `AuthContext` guarda `vigencia` (`undefined` = aún no se sabe tras recargar: `Panel` consulta `/auth/sesion`; `null` = no aplica). `/panel`: `por_vencer` → `AvisoCaducidad` (formulario solo desde ahí); `caducada` → `CambioObligatorio` (sin el resto del panel, con cerrar sesión). Un 403 `CONTRASENA_CADUCADA` en cualquier llamada lleva a esa pantalla (`setContrasenaCaducadaHandler` en `api.js`), no al login. El panel del barbero ya no tiene el cambio libre; el admin lo conserva en su menú de usuario. `/admin/empleados` muestra `IndicadorVigencia` (vigente, "Caduca en N días", caducada).

### Perfil del dashboard (foto y nombre de perfil; `/panel/configuracion` y `/admin/configuracion`)

- **Qué es.** Cada usuario (barbero o admin) puede ponerse una foto y un nombre que SOLO se ven dentro del dashboard. **Regla clave: no afecta la web pública.** Nuestro Equipo, la reserva, `PasoBarbero`, `/admin/empleados`, `/api/barberos` y la disponibilidad siguen leyendo `barberos.nombre` y `barberos.foto`, que ninguna parte de esta función escribe. El usuario de acceso (`usuarios.usuario`) tampoco se toca. Hay pruebas que lo demuestran (back: respuestas idénticas antes y después; front: guarda estática que impide que los archivos públicos importen el perfil).
- **Valor efectivo.** Barbero: nombre = `nombre_perfil ?? barberos.nombre`, foto = `foto_perfil ?? barberos.foto`. Admin: nombre = `nombre_perfil ?? usuarios.usuario`, foto = `foto_perfil` (sin foto pública: iniciales). Los nombres de perfil se pueden repetir.
- **Back-end** (`routes/perfil.js`, `controllers/perfilController.js`, `utils/perfil.js`): `verificarToken` carga `nombre_perfil`, `foto_perfil` y el nombre/foto públicos del barbero en su consulta de siempre (sin consulta extra), así que la contraseña caducada sigue dando 403 `CONTRASENA_CADUCADA` y un usuario inactivo 401 `SESION_INVALIDA`. `GET /api/perfil` devuelve `nombre`, `foto_url`, `foto_propia`, `nombre_perfil`, `usa_nombre_publico` y `usa_foto_publica`; `foto_url` es `/api/perfil/foto/<uuid>.<ext>` si `foto_propia` (ruta del back-end) o la ruta pública (`/Barberos/x.jpg`, del front) si no. Todos los errores llevan `codigo`.
  - **Nombre**: `PATCH` con solo `nombre_perfil`; recorte, espacios internos colapsados, sin caracteres de control ni invisibles (Cc/Cf), 2–40 caracteres (puntos de código). El HTML se guarda tal cual (React lo escapa).
  - **Foto**: `POST` con el cuerpo crudo (`express.raw` montado solo en esa ruta, sin multer ni dependencias; acepta cualquier `Content-Type` a propósito). Formato por **firma de bytes** (JPEG `FF D8 FF`, PNG con `IHDR`, WebP `RIFF…WEBP`): 415 `FORMATO_NO_PERMITIDO`, 413 `ARCHIVO_DEMASIADO_GRANDE` (> 2 MB), 400 `ARCHIVO_VACIO`. Sin SVG ni GIF, sin re-encode ni redimensión. Nombre del archivo = `crypto.randomUUID()` + extensión decidida por los bytes (nunca el nombre del cliente). Transacción con `SELECT … FOR UPDATE` de la fila del usuario; la foto anterior se borra solo tras el `UPDATE` correcto y, si algo falla, se borra la recién escrita. Límite: 10 subidas por usuario cada 15 min (429 `DEMASIADOS_INTENTOS`; se omite bajo `NODE_ENV=test` salvo `FORZAR_RATE_LIMIT_PRUEBA=true`).
  - **Servir** `GET /api/perfil/foto/:archivo`: sin autenticar; lista blanca `^[0-9a-f-]{36}\.(jpg|png|webp)$` (sin path traversal), `Content-Type` fijo por extensión, `X-Content-Type-Options: nosniff`, CSP `default-src 'none'; sandbox` y caché larga `immutable`.
- **Almacenamiento.** `backend/uploads/perfiles/` (fuera de `public/`; en `.gitignore`), o la carpeta de `UPLOADS_DIR` si se define (las pruebas usan una temporal, nunca la real). En Docker, el volumen nombrado `fotos_perfil_data` está montado en `/app/uploads` (así las fotos sobreviven a recrear el contenedor; el volumen de Postgres no se toca). Aplicar cambios del back-end con `docker compose up -d --build backend_black_iron`; **nunca `docker compose down -v`** (borraría los volúmenes, fotos incluidas).
- **Registro de cambios.** Solo si el rol es barbero y el valor EFECTIVO cambió de verdad (mismo nombre, o nombre de perfil igual al público, no registran). El admin no registra. Cada fila guarda el valor efectivo anterior y el nuevo.
- **Revisión del admin** (`controllers/adminPerfilController.js`): `GET /api/admin/cambios-perfil` → `{ total_barberos, barberos: [{ barbero_id, nombre (público), nombre_perfil, foto_url, foto_propia, ultimo_cambio, cambios: [{ id, usuario, campo, valor_anterior, valor_nuevo, creado_en }] }] }` (solo pendientes; el conteo es de BARBEROS distintos). `POST …/revisar { barbero_id }` marca como revisados todos sus pendientes (quién y cuándo). Si el barbero cambia algo después, vuelve a aparecer solo con lo nuevo. `POST /api/admin/barberos/:id/restablecer-perfil` pone `nombre_perfil` y `foto_perfil` a NULL en TODOS los usuarios de ese barbero, borra los archivos y marca sus cambios como revisados (no crea cambios nuevos), en una transacción.
- **Front.** `api.js` (`obtenerPerfil`, `actualizarPerfil`, `subirFotoPerfil`, `quitarFotoPerfil`; la foto se manda como `body: archivo` con el `Content-Type` del archivo; `obtenerCambiosPerfil`, `revisarCambiosPerfil`, `restablecerPerfilBarbero`). `context/PerfilContext.jsx` (`ProveedorPerfil`/`usePerfil`): una sola petición al montar el layout y **sin polling** (se actualiza con la respuesta de cada acción). El proveedor del panel se monta DESPUÉS de la comprobación de contraseña caducada: con el panel bloqueado nunca se pide el perfil. `utils/perfil.js`: validaciones iguales a las del back, `resolverUrlFoto` (la foto propia se resuelve contra el ORIGEN de `VITE_API_URL`, que ya incluye `/api`, y solo si tiene la forma exacta de la ruta del back-end), `barberoConPerfil` (nombre y foto del perfil sobre el barbero público; cargo y especialidad no cambian) y `mensajeErrorPerfil` (por `codigo`). `PanelLayout` pasa ese barbero a `ResumenBarberoProvider`: barra lateral (`PerfilBarbero`), menú de usuario, ventana de bienvenida y Mi cuenta se actualizan al instante. `MenuUsuario` muestra la foto (con fallback de iniciales si no carga) y la entrada "Configuración".
- **Página** `pages/Configuracion.jsx` (una sola, para las dos rutas, entradas en `menuBarbero.js`/`menuAdmin.js`): foto con vista previa antes de guardar, "Cambiar foto", "Quitar foto", nombre con contador 2–40 y validación en vivo, "Guardar" (deshabilitado sin cambios o inválido), "Usar mi nombre público" (manda `null`), nombre público y usuario de acceso de solo lectura, y el texto "Esta foto y este nombre solo se ven en tu panel…". Errores por código, éxito con `aria-live`, sin doble envío (`useRef`).
- **Aviso y vista del admin.** `context/CambiosPerfilContext.jsx` (`ProveedorCambiosPerfil`, montado en `AdminLayout`): UNA petición a `/api/admin/cambios-perfil` compartida por el aviso y la vista, con la misma lógica que el resumen del barbero (recarga con `recargar()`, al volver a la pestaña y cada 60 s; `AbortController` + bandera `vigente` contra respuestas obsoletas; si un refresco falla se conservan los datos; `descartar(id)` quita al barbero al instante tras una acción). `components/admin/AvisoCambiosPerfil.jsx`: igual que `AvisoPorConfirmar` (fijo, sin botón de cerrar, `z-20`, tarjeta a la derecha en escritorio y franja inferior en móvil, `role="status"` `aria-live="polite"` que solo cambia con el número), visible en TODO `/admin/*` mientras haya pendientes: "1 barbero ha cambiado su foto o nombre de perfil" / "N barberos han cambiado…", con el enlace "Revisar ahora" a `/admin/configuracion#cambios-perfil`. `components/admin/CambiosPerfilBarberos.jsx` (debajo del formulario propio, solo admin): una tarjeta por barbero (avatar actual, nombre público, nombre de perfil actual, cambios con valor anterior → nuevo, "Cambió su foto" y fecha relativa en hora de Bogotá), "Marcar como revisado" y "Restablecer perfil" (`ModalConfirmar` con foco en Cancelar). ### Catálogo de servicios

- `GET /api/servicios`: solo servicios activos, cada uno con `id`, `nombre`, `descripcion`, `precio`, `duracion_min`, `tipo` y `categoria` (`{ id, nombre, slug }`).
  - Filtros (todos opcionales y combinables): `area` (`barberia` | `asesoria`; sin él devuelve todo), `categoria` (slug), `tipo` (`original` | `elite` | `vip`), `q` (búsqueda por nombre, máx. 100 caracteres; `%`, `_` y `\` se escapan).
  - Orden: `ordenar` (`precio` | `duracion` | `nombre`) y `direccion` (`asc` | `desc`, requiere `ordenar`). Por defecto: categoría, precio y nombre.
  - `agrupar=categoria` devuelve `[{ categoria, servicios }]` en el orden de las categorías; las categorías sin resultados no aparecen.
- `GET /api/servicios/:id`: un servicio activo. 400 si el id no es numérico; 404 si no existe o está inactivo.
- `GET /api/categorias[?area=]`: `id`, `nombre`, `slug`, `orden` y `total_servicios` (solo activos; con `area`, solo categorías y servicios de esa área), en orden.
- Errores: 400 (con `error`) ante parámetros desconocidos, repetidos (`?tipo=a&tipo=b`, `?tipo[]=`) o con valor inválido, y ante una categoría que no existe.
- `POST /api/citas` y `GET /api/disponibilidad` responden **400 con `codigo: "SERVICIO_NO_DISPONIBLE"`** si el servicio no existe o está inactivo (`/api/disponibilidad` mantiene 404 para un id que no existe). El front usa ese `codigo` para devolver al cliente al paso Servicio.

### Reserva con varios servicios (carrito → reserva → paneles)

**Back-end** (`utils/serviciosCita.js`, `db/citaServicios.js`, `controllers/citasController.js`, `controllers/disponibilidadController.js`):

- **Una cita, varios servicios (máx. 3), atendidos seguidos por el mismo barbero como un solo bloque.** `cita_servicios` guarda una línea por servicio con su **snapshot** (`nombre`, `duracion_min`, `precio` al reservar, `orden` 1..3): renombrar o editar el servicio después no cambia la cita. `UNIQUE (cita_id, servicio_id)` (sin repetidos), `UNIQUE (cita_id, orden)` + `CHECK (orden BETWEEN 1 AND 3)` (el máximo de 3 también lo fuerza la base) y `ON DELETE CASCADE` (la única baja de citas es la limpieza de las demo). Índice por `servicio_id`.
- **`citas.duracion_min` y `citas.precio` son la SUMA de las líneas** y `citas.servicio_id` es el servicio principal (el primero). Así `rango`, el `EXCLUDE citas_sin_solapamiento`, los ingresos y el ticket promedio no cambian. Todo se calcula en el servidor con lo que hay en la base; cualquier total, precio o duración que mande el cliente se ignora.
- **`POST /api/citas`** acepta `servicios_ids` (array de 1 a 3 enteros positivos como `number` JSON, sin repetidos; strings, objetos o arreglos anidados → 400 `DATOS_INVALIDOS` con `campo`) o el `servicio_id` anterior (equivale a `[servicio_id]`). Los dos a la vez → 400. Códigos estables (todos 400): `SERVICIO_NO_DISPONIBLE` (con `servicios_no_disponibles: [ids]`), `SERVICIOS_REPETIDOS`, `LIMITE_SERVICIOS`, `DURACION_EXCEDIDA` (con `duracion_total_min` y `maximo_min`). Todo ocurre en UNA transacción con un cliente del pool: `SELECT … FOR SHARE` de los servicios (ordenados por id: una baja concurrente espera y la reserva no se hace sobre algo que se desactiva), `INSERT` de la cita y de las líneas; ante `23P01`/`40P01` hay `ROLLBACK` completo antes de probar el siguiente barbero y la conexión siempre se libera.
- **Tope de 240 min SOLO para combos (2 o más servicios).** Un servicio individual se puede reservar aunque dure más (el catálogo admite hasta 600 min); lo limita únicamente el horario de atención. `MAX_SERVICIOS_POR_CITA` y `MAX_DURACION_TOTAL_MIN` viven en un solo lugar (`utils/serviciosCita.js`; el front los repite en `utils/carrito.js`).
- **`GET /api/disponibilidad`** acepta `servicios=1,2,3` (CSV estricto: sin espacios ni vacíos, sin repetidos, máx. 3) o `servicio=<id>` (formato anterior, mismas respuestas de siempre: 404 si no existe, 400 `SERVICIO_NO_DISPONIBLE` si está inactivo). Los dos a la vez → 400. El cierre y los solapamientos usan la duración total.
- **Respuestas de citas** (crear, `GET /api/citas`, PATCH, `/api/admin/citas`, `/api/barbero/*`): mantienen `servicio_id` (principal) y `servicio_nombre` (nombres unidos con " + ") y añaden `servicios: [{ id, nombre, duracion_min, precio }]` ordenados por `orden`, tomados del snapshot. `q` del admin y de "Mis citas" busca en los nombres de TODOS los servicios (`EXISTS` sobre `cita_servicios`). "Por confirmar" usa la duración total de la cita.
- **Estadísticas**: `serviciosTop` (y con él el reporte diario y su CSV) cuenta por **línea** (`cantidad` = líneas, `ingresos` = SUM del precio de la línea): una cita con 3 servicios suma 1 a cada uno. Ingresos, ticket promedio, canceladas y **`total_cortes` cuentan CITAS, no servicios** (un combo de 3 servicios es 1 corte). Por eso la suma de `cantidad` de `servicios_mas_pedidos` puede superar a `total_cortes`.
- **Migración**: `schema.sql` crea `cita_servicios` y hace un backfill idempotente (`INSERT … SELECT … WHERE NOT EXISTS`): una línea por cita sin líneas, con duración y precio de la propia cita y el nombre actual del catálogo solo para ese snapshot inicial. `seedDemo` y los helpers de prueba (`utilsPrueba.js`: `insertarCita`, `insertarCitaConServicios`) insertan también las líneas.

**Front — carrito "Tu selección"** (`context/CarritoContext.jsx`, `components/carrito/`, `utils/carrito.js`):

- `ProveedorCarrito` vive en `Landingpage` (sobrevive a la navegación carta ↔ reserva). Estado: lista ordenada de ids (máx. 3) en `sessionStorage` (`seleccion-servicios`, todo con try/catch; sin storage funciona en memoria; un valor guardado inválido se descarta). Al cargar la carta y al abrir el panel móvil se valida contra `GET /api/servicios`: los ids inactivos o inexistentes se quitan con un aviso (`aria-live`).
- Reglas del cliente en **un solo lugar**, `utils/carrito.js` (la carta, el carrito y el paso 1 de la reserva la comparten): máximo 3, tope de 240 min solo para combos, aviso suave de misma categoría y `estadoDeTarjeta` (bloqueado/ayuda). Un botón que no se puede usar queda con `aria-disabled` (sigue enfocable) y su motivo se ve en texto enlazado con `aria-describedby` (no solo color).
- Escritorio (lg+): aside pegajoso a la derecha en `CatalogoServicios` (rejilla `lg:grid-cols-[minmax(0,1fr)_20rem]`; tarjetas `xl:grid-cols-3`). Móvil: barra fija inferior `z-40` de **64 px** (el botón de WhatsApp flota a 68 px sobre el borde inferior: no subir esa altura) y panel deslizable `z-55` (sobre WhatsApp/navbar `z-50`, bajo el menú móvil `z-60/70`) con `useAtraparFoco`. La barra de `ResumenReserva` (reserva) también es `z-40` y mide ≤ 61 px por lo mismo.
- Tarjeta de la carta: "Agregar a mi selección" / "Quitar de mi selección" (`aria-pressed`) y el enlace "Reservar solo este" (`?servicio=<id>`, camino rápido, no toca el carrito). "Agendar N servicio(s)" navega a `/reservar-corte?servicios=1,2,3`.

**Front — flujo de reserva** (`pages/ReservaCorte.jsx`, `components/sections/reserva/`, `utils/seleccionReserva.js`):

- **El flujo tiene su propio estado** (`reservaReducer`: `servicioIds[]` en orden, máx. 3, sin repetidos) que **arranca desde la URL y nunca está ligado al carrito**. `leerServiciosDeUrl`: `?servicios=1,2,3` (ignora basura y repetidos, recorta a 3) o `?servicio=<id>`; si vienen los dos manda `?servicios=` cuando trae al menos un id válido.
- **Decisión: el carrito se vacía al reservar con éxito SOLO si la reserva llegó con `?servicios=` (vino del carrito).** Una reserva por el camino rápido (`?servicio=`) o sin parámetros no toca el carrito, y lo que se cambie en el paso 1 tampoco lo modifica. Una reserva que falla no lo vacía. Limitaciones conocidas: (1) quien reserva por `?servicio=` con el carrito lleno lo sigue viendo lleno (es lo que se quiso: no se asume que esos servicios ya se agendaron); (2) como el carrito se vacía por el origen de la URL y no por coincidencia de ids, si el cliente cambió la selección dentro del paso 1 y reservó otros servicios, el carrito se vacía igual; (3) abrir a mano una URL `?servicios=` sin carrito no tiene efecto sobre él.
- `PasoServicio` es multiselección con las mismas reglas del carrito; `PasoFechaHora`/`obtenerDisponibilidad` envían `servicios=1,2,3`; cambiar la selección invalida fecha y hora. `ResumenReserva` (tarjeta lateral y barra móvil), `ModalConfirmacion` y `PantallaExito` muestran la lista de servicios, la duración total y el total; con un solo servicio se ven exactamente como siempre. `crearCita` envía `servicios_ids`.
- Errores del servidor: `SERVICIO_NO_DISPONIBLE` (con `servicios_no_disponibles`) quita **solo** esos ids y conserva el resto (aviso `MENSAJE_SERVICIOS_NO_DISPONIBLES`; si era el único, el aviso de siempre); `SERVICIOS_REPETIDOS`, `LIMITE_SERVICIOS` y `DURACION_EXCEDIDA` vuelven al paso Servicio con el motivo y la selección intacta; el choque de horario (409) sigue volviendo al paso Fecha y hora. Un id inactivo en la URL se trata igual. Un combo de la URL que pasa de 240 min se avisa al cargar.
- Todos los controles de la reserva miden ≥ 44 px (`min-h-11`), incluidos los chips de filtro (`FiltrosServicios`, compartidos con la carta).

**Front — paneles**: `components/ui/ServiciosDeCita.jsx` y `esCombo` (`utils/servicios.js`) muestran los servicios de una cita. Ingresos = `SUM(citas.precio)` de las completadas (precio guardado en la cita). Las canceladas no suman y se cuentan aparte. El ticket promedio excluye las completadas de precio 0. Las series usan `generate_series(0, n)` sumado a una fecha (no dependen de la zona de la sesión de Postgres). `/estadisticas/ingresos` devuelve 30 días (o 12 meses) y los 30 (12) anteriores. Las consultas SQL viven en `backend/db/estadisticas.js`.

Paginada: `limite` por defecto 10, máximo 50 (la pantalla pide 15). `q` busca en cliente, servicio y barbero (escapa `%`, `_` y `\`). `fecha`/`hora` salen como texto.

Categoría: slug generado del nombre (con sufijo `-2`, `-3`… si choca); desactivar una con servicios activos → 409 `CATEGORIA_CON_SERVICIOS`. Todos los errores llevan `codigo` estable (`DATOS_INVALIDOS` con `campo`, `NOMBRE_DUPLICADO`, `CATEGORIA_NO_DISPONIBLE`, `SERVICIO_INCOMPLETO`, `CATEGORIA_CON_SERVICIOS`, `SLUG_NO_EDITABLE`, `*_NO_ENCONTRADO`, `ID_INVALIDO`). Editar precio o duración no altera las citas ya creadas (guardan su propio precio y duración). `/api/servicios` y `/api/categorias` (públicas) solo muestran lo activo y nada de una categoría inactiva.

Campos desconocidos → 400 `DATOS_INVALIDOS`; códigos: `USUARIO_DUPLICADO`, `EMPLEADO_NO_ENCONTRADO`, `ID_INVALIDO`, `PARAMETRO_INVALIDO`.
- **Reporte diario** (`adminReportesController.js`): un solo día, sin desglose por barbero, con las mismas reglas que las estadísticas (reutiliza `resumenPeriodo` y `serviciosTop` de `db/estadisticas.js`). Respuesta: `fecha`, `total_cortes` (citas completadas: **cuenta CITAS, no servicios**; un combo de 3 servicios es 1 corte), `ingresos` (SUM de `citas.precio` de las completadas: el precio de la cita, no el actual del servicio), `ticket_promedio` (excluye precio 0), `canceladas` (aparte, no suman), `pendientes_sin_cerrar` (todas las `pendiente` de ese día) y `servicios_mas_pedidos` (hasta 10, con `nombre`, `cantidad` e `ingresos`; **cuenta por línea de `cita_servicios`**: cada servicio de cada cita completada suma 1). Un día sin citas da ceros y lista vacía. Errores con `codigo`: `FECHA_INVALIDA` (formato o fecha inexistente como 2026-02-31), `FECHA_FUTURA` (se compara contra `hoyISO()` de Bogotá, calculado en Node) y `PARAMETRO_INVALIDO` (parámetro desconocido o repetido). El CSV (`utils/csv.js`) usa `;`, BOM UTF-8, CRLF, comillas dobles escapadas duplicándolas y neutraliza fórmulas (si una celda de texto empieza con `=`, `+`, `-`, `@`, tabulación o retorno se le antepone `'`); `Content-Type: text/csv; charset=utf-8` y `Content-Disposition: attachment; filename="reporte-diario-AAAA-MM-DD.csv"`.

Completar solo si `fecha` ≤ hoy en Bogotá; una cita futura se puede cancelar (barbero) o reasignar (admin), no completar. Las pendientes de un día/hora pasados se marcan "Vencida" (informativo: las cierra el barbero); el aviso del reporte diario lo dice y enlaza a `/admin/citas`.

Cualquier filtro reinicia la página; una página inexistente lleva a la última válida; 15 citas por página; tras reasignar la lista se recarga conservando página y filtros.

### Panel del barbero (API)

- Rutas bajo `/api/barbero` (`routes/barbero.js`, `controllers/barberoController.js`, consultas en `db/barbero.js`), solo lectura, con `verificarToken` + `requiereRol('barbero')`: sin token 401, admin 403, contraseña caducada 403 `CONTRASENA_CADUCADA`, usuario desactivado 401 `SESION_INVALIDA`. No hay POST/PATCH/DELETE.
- **El `barbero_id` sale siempre de `req.usuario` (base de datos)**, nunca de query, body ni params. Ninguna de las tres rutas admite parámetros: cualquiera (conocido o no, repetido o `a[]=`) da 400 `PARAMETRO_INVALIDO`. Otros códigos: `SIN_BARBERO` (403, usuario de barbero sin barbero ligado).
- **Cita "por confirmar"**: pendiente cuyo **fin** (inicio + duración guardada en la cita, y si no hubiera la del servicio) **+ 2 horas** ya pasó, incluidos días anteriores. `fecha + hora + duración + gracia <= ahora`: en el instante exacto del límite ya cuenta, un minuto antes no. "Ahora" lo decide Node (`ahoraBogota()`) y llega como parámetro; la gracia vive en `backend/utils/confirmacion.js` (`HORAS_GRACIA_CONFIRMACION = 2`, `TOPE_POR_CONFIRMAR = 100`). La condición SQL está una sola vez en `db/barbero.js`.
- `GET /api/barbero/resumen` → `fecha` (hoy, Bogotá), `citas_hoy` (no canceladas), `completadas_hoy`, `pendientes_hoy`, `proxima_cita` (`{ id, cliente, servicio_nombre, fecha, hora }` de la pendiente más cercana que aún no empieza, hoy o días siguientes; o `null`), `ingresos_hoy`, `cortes_mes`, `ingresos_mes` (solo SUS completadas, precio guardado en la cita, mes en curso de Bogotá) y `por_confirmar`. Reutiliza `resumenPeriodo` de `db/estadisticas.js` (que ahora acepta un `barberoId` opcional).
- `GET /api/barbero/citas-por-confirmar` → `{ total, tope, items }`: sus vencidas de la más antigua a la más reciente (máx. 100; `total` es el conteo real), cada una con `id`, `cliente`, `servicio_nombre`, `fecha`, `hora`, `duracion_min`, `termino_hace_min` (desde que terminó la cita) y `vencida_hace_min` (desde que pasó el límite).
- `GET /api/barbero/agenda-hoy` → `{ fecha, citas }`: sus citas de hoy por hora (incluye canceladas) con `id`, `cliente`, `servicio_nombre`, `fecha`, `hora`, `estado`, `duracion_min`, `precio` y `por_confirmar`. Sin correo ni teléfono.
- `GET /api/barbero/citas?pestana=&q=&desde=&hasta=&pagina=&limite=` (lista paginada de "Mis citas"; `controllers/barberoController.js` → `listarMisCitas`, consulta en `db/barbero.js` → `listarCitasBarbero`). Solo sus citas (el `barbero_id` sale de `req.usuario`). Parámetros desconocidos o repetidos → 400 `PARAMETRO_INVALIDO`; valores inválidos → 400 `PARAMETRO_INVALIDO` con `campo` (`pestana`, `q` > 100 caracteres, `desde`/`hasta` no son fecha real o `desde` > `hasta`, `pagina` 1–1 000 000, `limite` 1–50). Sin POST/PATCH/DELETE (404).
  - `pestana` (por defecto `hoy`): `hoy` (de hoy, no canceladas, por hora) · `proximas` (pendientes que aún no empiezan, las más cercanas primero) · `por_confirmar` (regla de las 2 h, la misma condición SQL de `db/barbero.js`; de la más antigua a la más reciente) · `completadas` y `canceladas` (más recientes primero) · `todas` (más recientes primero). "Hoy" y "ahora" los decide Node (Bogotá) y llegan a SQL como parámetro.
  - `q` busca en cliente o nombre del servicio (ILIKE; `%`, `_` y `\` se escapan; solo espacios = sin filtro). `desde`/`hasta` son inclusivos. `limite` por defecto 10 (la pantalla pide 15).
  - Respuesta: `{ items, pagina, limite, total, conteos }`. `total` es el de la pestaña pedida; `conteos` = `{ hoy, proximas, por_confirmar, completadas, canceladas, todas }` con los MISMOS filtros `q`/fechas (lo que dice cada pestaña es lo que verás al abrirla). Una página fuera de rango devuelve `items` vacíos con el `total` (convención de `/api/admin/citas`; el front pasa a la última válida). Cada ítem: `id`, `cliente`, `servicio_nombre`, `duracion_min`, `fecha` y `hora` (texto), `estado`, `precio` (el de la cita) y `por_confirmar`. Sin correo ni teléfono.
- **Estadísticas personales** (`GET /api/barbero/estadisticas`, `/estadisticas/ingresos`, `/estadisticas/servicios-top`): los MISMOS controladores del admin (`controllers/estadisticasController.js`, que ahora los construye con `crearControladores(alcance, conCodigo)`) y las mismas consultas de `db/estadisticas.js`, que aceptan un `barberoId` opcional (`resumenPeriodo`, `ingresosPorDia`, `ingresosPorMes`, `serviciosTop`). El `barbero_id` sale de `req.usuario` (nunca de la petición: `?barbero_id=` es un parámetro desconocido → 400); sin barbero ligado → 403 `SIN_BARBERO`. Mismos parámetros, formas de respuesta y reglas de "hoy" en Bogotá (Node) que `/api/admin/estadisticas` (ver "Dashboard del administrador"); los 400 del barbero llevan además `codigo: 'PARAMETRO_INVALIDO'` (los del admin siguen sin `codigo`). Solo lectura (404 con otros métodos). Nunca devuelven datos de otros barberos ni comparativas entre barberos.
- Distinto de `vencida` del admin (`GET /api/admin/citas`): allí es "la hora de inicio ya pasó" (informativo); "por confirmar" es la regla de arriba.

### Seed del catálogo

- `npm run seed` **solo inserta lo que falta** (`INSERT … ON CONFLICT DO NOTHING`): nunca hace UPDATE, nunca reactiva y nunca desactiva. Lo que el admin edite (precio, nombre, descripción, `activo`…) sobrevive a cualquier seed, y los servicios del admin (`clave_seed` nulo) no se tocan jamás. Las categorías y los servicios (39 de barbería + 3 de asesoría) salen de `backend/db/data/servicios.js` y `descripciones.js`; el `id` de esos archivos solo sirve para casar cada servicio con su descripción.
- Cada categoría y servicio de los datos lleva una `clave` **estable** (se guarda en `clave_seed`): `validarCatalogo` exige claves únicas y no vacías. Nunca cambies una clave publicada; así un servicio que el admin renombró no se vuelve a crear. Un servicio nuevo en el catálogo = una clave nueva.
- Pasos únicos (`backend/db/migracionesCatalogo.js`, registrados en `migraciones_aplicadas`, se ejecutan al arrancar el backend y al correr el seed): (1) asignar `clave_seed` a las filas existentes que coinciden con el catálogo (servicios por nombre, categorías por slug); (2) desactivar los 6 servicios del catálogo anterior, solo cuando el catálogo nuevo ya está en la base. Si ya estaban inactivos solo se registra; si el admin reactiva uno, nada lo vuelve a apagar.
- `npm run seed -- --restablecer-catalogo [--confirmar]` (solo desarrollo; se niega con `NODE_ENV=production`): vuelve las filas del catálogo a los datos de los archivos. Sin `--confirmar` solo muestra qué sobrescribiría.
- Los ids reales los asigna la secuencia, así que hay **huecos** y no coinciden con los de los archivos. No usar esos ids como referencia.
- Se puede correr las veces que haga falta sin duplicar ni pisar nada.

### Datos de demostración del portafolio (`sembrarDemo.js`)

- **Qué es.** `backend/db/sembrarDemo.js` (`npm run sembrar:demo`) deja la base de DESARROLLO lista para mostrar el proyecto: ~1 870 citas ficticias entre 40 días atrás y 14 días adelante, coherentes con el horario 10:00–20:00. Es distinto de `seed:demo` (más simple, marca `[demo] `): el de portafolio es el que se usa para mostrar.
- **⚠️ Nunca en producción.** Se niega con `NODE_ENV=production` y contra una base con "test" en el nombre. Sin `--confirmar` solo simula (planifica y muestra el resumen sin escribir).
- **Cómo reconoce sus filas.** El correo de la cita termina en `@demo.blackiron.example` (dominio reservado que no existe); los teléfonos son `3000000NNN`. Al re-ejecutar borra SOLO esas citas, por id exacto (`cita_servicios` y `asesoria_gratis_usos` caen en cascada) y las recrea, todo en UNA transacción: si algo falla no queda nada a medias. No toca citas reales, usuarios, barberos, servicios ni contraseñas, y no desactiva ninguna restricción (`citas_sin_solapamiento`, triggers de área, UNIQUE de la gratis).

## Convenciones de código

- **No** importar `React` en componentes (React 19 no lo necesita).
- Importar **solo** de `react-router-dom`, nunca de `react-router`.
- Ningún dato repetido a mano en JSX: 3+ elementos similares van como array en `src/data/` (o vienen de la API) y se renderizan con `.map()`.
- Los servicios (nombre, descripción, precio, duración, tipo, categoría) tienen **una sola fuente de verdad**: la API. El front ya no deduce nada por nombre (se eliminaron `categoriasServicios.js` y `descripcionesServicios.js`).
- Precios siempre con `formatearPrecio` (`src/utils/formato.js`): da `$18.000` y "Gratis" si el precio es 0. Nunca formatear a mano.
- Catálogo y paso 1 de la reserva comparten `FiltrosServicios`, `useFiltroServicios`, `InsigniaTipo` (Original / Élite / VIP) y `TarjetaServicio`. Los filtros son botones con `aria-pressed` dentro de `role="group"` (no `role="tab"`); la lista se carga una vez y se filtra en el cliente. Los errores de carga usan `ErrorCarga` (`role="alert"` + "Reintentar").
- Responsive: en un contenedor `grid` que tenga hijos con scroll interno (`overflow-x-auto`), usar `grid-cols-1` y `min-w-0` en el hijo. Sin eso, la columna automática se estira al ancho del contenido y desborda la página en móvil. Medir con `scrollWidth` vs `clientWidth` en 360–414 px.
- Todas las llamadas HTTP pasan por `src/services/api.js`.
- "Hoy" en el front es siempre `hoyISO()` de `src/utils/fechas.js` (America/Bogota); no usar `new Date().toISOString()`.
- Totales de dinero (ingresos, ticket promedio) con `formatearDinero` (muestra `$0`); `formatearPrecio` es solo para el precio de un servicio (0 = "Gratis"). Las variaciones con `formatearDelta` (devuelve "—" sin base, nunca NaN ni ∞).
- Gráficos del dashboard: SVG propio, sin librerías, con colores y trazos en clases de Tailwind (`fill-oro`, `stroke-zinc-600`). Cada gráfico lleva `role="img"` + `aria-label` y una tabla de datos dentro de un `div` `sr-only` (una `<table>` suelta con `sr-only` ensancha la página).
- Descargas con token: el enlace directo no lleva el `Authorization`, así que el CSV se pide con `fetch` en `api.js` y se guarda con `guardarArchivo` (`src/utils/descarga.js`).
- Impresión: se hace con variantes `print:` de Tailwind (nada de CSS propio). `AdminLayout`, `BarraLateral` y `BarraSuperior` ya llevan `print:hidden`/`print:bg-white`; en una página imprimible, los controles llevan `print:hidden` y las tarjetas `print:bg-white print:text-black`.
- Listados del admin: el estado (pestaña, búsqueda, fechas, página) va en la URL con `useSearchParams`; los datos se piden con `useCarga` (conserva los datos mientras llegan los nuevos y descarta respuestas viejas).
- Toda imagen lleva `alt` descriptivo, nunca `alt=""`.
- La foto de un barbero se muestra siempre con `AvatarBarbero` (`src/components/ui`): si no hay foto o no carga, usa un avatar con iniciales hecho con clases de Tailwind. Los barberos creados desde el admin no tienen foto.
- Los listados ordenados por nombre se ordenan en el front con `localeCompare(…, 'es')` (así "Ángel" va antes de "Boby"), nunca con `<` ni con el orden del back-end.
- Todo input tiene `<label htmlFor>` enlazado a su `id`.
- Usar `<Link>` / `<NavLink>` para navegar, nunca `<a href>` interno.
- Consultas SQL siempre parametrizadas (`$1, $2`), nunca concatenar strings.

## Seguridad — reglas que NO se negocian

- Nunca hardcodear contraseñas, secretos o connection strings en código ni en `docker-compose.yml`. Todo va en `.env` (no versionado) y se referencia con `${VARIABLE}`.
- Las contraseñas se guardan SIEMPRE hasheadas con bcrypt y **nunca** se devuelven en ninguna respuesta de la API.
- Los permisos se aplican **en el back-end**: filtrar citas por el `barbero_id` del token, no por lo que mande el cliente. Ocultar botones en el front no es seguridad.
- La doble reserva se evita con el `UNIQUE` de la base de datos; responder `409` ante el error `23505`.
- Validar el body de cada endpoint antes de tocar la base de datos.
- CORS restringido a `FRONTEND_URL`; rate limiting en el login.
- **Límite de intentos del login** (`routes/auth.js`): DOS limitadores que cuentan solo los intentos FALLIDOS (`skipSuccessfulRequests`; un login correcto no gasta cupo): (a) por **IP + usuario normalizado** (trim + minúsculas, máx. 100 caracteres): 10 / 15 min (`LIMITE_LOGIN_USUARIO_RATE`); (b) por **IP**: 100 / 15 min (`LIMITE_LOGIN_IP_RATE`), freno contra probar muchos usuarios desde una IP. Quien falla con un usuario NO bloquea a los demás usuarios de la misma IP. No hay límite por usuario en todas las IPs (permitiría dejar fuera a un barbero a propósito). Sin `usuario` o no texto → clave fija (queda limitado por IP). Se evalúa primero el de usuario (si ya está bloqueado no gasta el cupo de IP). Respuesta 429 idéntica en ambos y sin revelar si el usuario existe: `{ error, codigo: 'DEMASIADOS_INTENTOS', reintentar_en_seg }`. El contador no se reinicia con un login correcto (solo caduca la ventana). Las claves usan `ipKeyGenerator` (IPv6). Pruebas: `rateLimitLogin.test.js` y `rateLimitLoginPorUsuario.test.js` (límites bajos por entorno; `app.set('trust proxy', true)` solo en la app de la prueba para simular IPs con `X-Forwarded-For`).
- No reescribir el historial de git (`filter-repo`, `rebase` sobre commits ya pusheados) sin confirmación explícita.
- No hacer commit de `.env` reales; solo `.env.example` con placeholders.
- La contraseña de Postgres que estuvo en el repo público se considera comprometida: no reutilizarla.
- No reescribas el historial de git ni hacer commits.
- Si no tienes claro algun cambio, preguntame no inventes ni empiezes a divagar.

### Política de contraseñas (`utils/politicaContrasenas.js`)

8–72 **bytes** (más largo se rechaza, no se trunca), no común (lista pequeña, sin distinguir mayúsculas/acentos ni símbolos finales), no un solo carácter repetido ni secuencia obvia (`12345678`, `abcdefgh`), y no el usuario ni «usuario + poco» (`rafa1234`; el usuario dentro de una frase larga sí vale). Sin reglas de composición. Se aplica al crear usuario (`POST /api/admin/usuarios`), crear empleado, restablecer (`PATCH /api/admin/usuarios/:id`), cambiar la propia y al sembrar el admin (`ADMIN_PASSWORD` ≥ 12). Error: 400 `CONTRASENA_DEBIL` (con `campo`). bcrypt coste 10 (`COSTO_BCRYPT`, un solo lugar; subirlo bloquea más el bucle de eventos porque `bcryptjs` es JS puro).

### Límites vigentes y probabilidad práctica de adivinar el código del correo

Login: 10 fallos/15 min por IP+usuario y 100/15 min por IP (ver «Límite de intentos del login»). Código de 6 dígitos: 5 intentos por código (exacto, también con 50 peticiones paralelas), 5 códigos/hora y 60 s entre códigos por correo exacto → como máximo 25 intentos por hora y correo: P ≈ 2,5·10⁻⁵ por hora (≈ 28 000 h de media para acertar). Por IP: 30 confirmaciones/15 min y 20 solicitudes/hora.

### Qué resistió el ataque

Inyección SQL (≈ 840 peticiones con comillas, UNION, apilados, bytes nulos, unicode, 1 MB, tipos raros en query/ruta/cuerpo; todo parametrizado), `alg: none`, firma alterada, confusión HS/RS con PEM, secretos comunes, tokens expirados, payload con `rol` falso (el rol sale de la base), límite del login con cabeceras de IP falsas / mayúsculas / espacios / 60 peticiones simultáneas, matriz ruta × rol (35 rutas × anónimo/expirado/barbero/asesor/admin coherente), IDOR de citas (404 para citas ajenas), reasignación entre áreas, asignación masiva (claves desconocidas → 400), estados finales, CORS (nunca refleja el origen), recorrido de directorios, subida de fotos (firma de bytes, nombre/extensión decididos por el servidor, SVG/HTML/PHP/GIF → 415, `nosniff` + CSP `sandbox`), comprobante del correo (manipulado, otro correo, `typ`/`aud` erróneos, token de login como comprobante y al revés, doble reserva simultánea con un comprobante → solo 1), cabeceras/HTML de los correos (nombres con `<img onerror>`, `Bcc:`, CRLF), XSS en el front con Chrome headless (admin, barbero, URLs con HTML: 0 alertas, el texto sale escapado).

### Pendiente / depende del entorno (ver `checklist-sesiones.md`)

- `NODE_ENV=production` es **obligatorio** en el despliegue; sin definirlo el arranque avisa en consola.
- Token de sesión en `localStorage` (riesgo ante XSS; hoy no se encontró ninguno). Mitigación: CSP estricta en el hosting del front; migrar a cookie `HttpOnly` es un rediseño.
- Cierre de sesión solo del lado del cliente: el token vale hasta 8 h o hasta que suba `version_token`. Un `POST /api/auth/logout` que lo incremente exigiría tocar el flujo del front (no hecho).
- `trust proxy` sin configurar y limitadores en memoria (ver «Notas operativas»).
- `POST /api/asesorias/gratis/comprobar` sigue siendo un oráculo (no se cambió; ver «Verificación de correo»).
- Un correo con `+alias` o puntos de Gmail cuenta como otro para los topes por correo: se puede enviar el código a un mismo buzón con alias distintos (acotado por 20 solicitudes/hora/IP). Mitigación real: WAF/CAPTCHA o un tope global.

## Cómo trabajar en este repo

- Cada sesión se enfoca en **un bloque** del checklist; no mezcles bloques salvo que se pida.
- Antes de dar una tarea por terminada: `npm run lint` en el front y que `npm start` levante sin errores en el back.
- Verifica los permisos con pruebas reales (por ejemplo, que un barbero no pueda ver ni modificar citas de otro).
- Si algo es ambiguo y no afecta seguridad ni arquitectura, elige la opción más estándar y continúa.
- Si la decisión afecta seguridad, permisos, datos de la base o borra archivos, pregunta antes.
- Siempre usar tailwind, nunca usar ccs puro ni crear archivos innecesarios.
- Siempre trabajar pensando en que la pagina debe ser responsive, SIEMPRE.
- No hagas commits ni push, ni locales ni remotos. El desarrollador los hace manualmente. Al terminar cada bloque, indica qué archivos cambiaron y detente para que lo revise.
